# Shared API contract (MVP)

Same origin JSON REST. camelCase JSON, string enums. Guid ids as strings. UTC ISO timestamps. EUR. Errors ProblemDetails {title,detail,status}. All successful collections are arrays (not paged objects initially). Authentication cookies, credentials same-origin. GET /api/session returns {user:null|{id,email,displayName,role},csrfToken,demoEnabled,stagingDemoEnabled}. Send X-CSRF-TOKEN on all mutations, including auth. Roles Customer, Worker, Admin. Missing session 401, wrong role 403. Frontend API helper refreshes session token after login/logout.

POST /api/auth/register {email,password,displayName,phone,locality,role:Customer|Worker}; POST /api/auth/login {email,password}; POST /api/auth/logout {}. Return session user or 204. POST /api/auth/forgot-password {email} returns {message}; 503 if no mail configured. POST /api/auth/reset-password {email,token,password}. POST /api/auth/demo {persona:customer|worker|admin} development only; server chooses fictional personas. No production privileged public credentials.

GET /api/catalog -> Category[] {id,slug,name,description,icon,modes:string[],requiresVerification,isActive}. Modes ForMe,WithMe,TeachMe. GET /api/localities -> {name,latitude,longitude}[] (Malta and Gozo reference coordinates). Public GET /api/workers?categoryId=&mode=&locality=&availableNow=&maxPrice=&startAt=&durationMinutes= -> Worker[] {id,userId,displayName,bio,locality,yearsExperience,verificationStatus,availableNow,availabilityUpdatedAt,isDemo,hourlyRate,pricingType,categoryIds:string[],modes:string[],reviewCount,averageRating:number|null}. GET /api/workers/{id} -> above plus {offerings:Offering[],availability:AvailabilityWindow[],reviews:Review[]}; Offering {categoryId,modes:string[],pricingType:Hourly|Fixed|Quote,price}; Review {id,rating,comment,customerName,createdAt}. Public rows never include email or private coordinates/addresses. Radius matching uses locality coordinates/Haversine or SQL spatial, not string proximity.

GET /api/me -> {id,email,displayName,phone,locality,role}; PUT /api/me {displayName,phone,locality}; GET/POST /api/me/addresses {id?,label,address,locality}; DELETE /api/me/addresses/{id}. POST /api/me/privacy-request {kind:Export|Delete} -> {message} records admin task, not immediate erasure.

GET /api/worker/profile -> Worker detail incl {radiusKm,offerings,availability}; PUT /api/worker/profile {displayName,bio,locality,yearsExperience,radiusKm,hourlyRate,categoryIds,modes,pricingType} creates/updates worker offerings; PUT /api/worker/availability {availableNow,windows:[{dayOfWeek:0..6,startTime:"08:00",endTime:"17:00"}],exceptions:[{date:"2026-10-20",isAvailable:false}]} ; POST /api/worker/verification {reference,notes} submits material for admin review. Suspended workers receive 403 without changes. Existing Verified approval is preserved; other eligible states become Pending. Every successful submission is audited; only admins can reject or suspend approval. Regulated work needs admin approval; modes for plumbing/electrical only ForMe. Profiles and verification states distinguish Unverified,Pending,Verified,Rejected,Suspended.

GET /api/bookings -> owned Booking[] (assigned worker or customer; admin all). GET /api/bookings/{id} -> owned Booking. POST /api/bookings {workerId,categoryId,mode,summary,description,address,locality,startAt,durationMinutes,isAsap,idempotencyKey} -> Booking. Booking {id,customerId,workerId,workerName,customerName,categoryId,categoryName,mode,summary,description,locality,address:string|null,startAt,endAt,status,pricingType,amount:number|null,commissionAmount:number|null,isSimulated:true,quoteAmount:number|null,history:[{status,at}],review:Review|null}. Status Requested,Quoted,WorkerAccepted,Confirmed,InProgress,Completed,Cancelled,Expired. No private address to worker before Confirmed. POST /api/bookings/{id}/action {action:accept|decline|quote|confirm|start|complete|cancel,amount?:number} -> Booking. Worker accept reserves slot transactionally (Requested->WorkerAccepted); quote Requested->Quoted; customer confirm Quoted or WorkerAccepted->Confirmed, reserves atomically. start/complete worker; cancel owner prior to in progress. Quote explicit confirm; hourly amount rate*duration. Confirmation checks price/state & ownership. SQL transaction locks worker row before interval checks (holds to commit), unique request idempotency and booking/payment indexes. Completion creates simulated payment+commission once. POST /api/bookings/{id}/review {rating,comment} -> Review customer only completed once.

GET /api/admin/overview -> {customers,workers,pendingVerifications,openRequests,confirmedBookings,completedBookings,cancelledBookings,simulatedGross,simulatedCommission,commissionPercent}; GET /api/admin/workers -> Worker[] plus {verificationReference,verificationNotes}; POST /api/admin/workers/{id}/verification {status:Verified|Rejected|Suspended}; GET /api/admin/users -> {id,email,displayName,role,isSuspended}[]; POST /api/admin/users/{id}/status {isSuspended}; POST /api/admin/categories (Category fields); PUT /api/admin/categories/{id} (same); PUT /api/admin/settings {commissionPercent}; GET /api/admin/audit -> {id,action,actorId,createdAt,details}[]; GET /api/admin/payments -> {id,bookingId,amount,commissionAmount,status,isSimulated,createdAt}[]; GET /api/admin/privacy-requests -> task rows. Admin operations audit.

GET /health/live and /health/ready. GET /openapi/v1.json development. SPA routes /, /services, /services/:slug, /find, /workers/:id, /join, /login, /register, /dashboard, /worker, /account, /bookings/:id, /admin, /privacy, /terms. Server SEO title/description/canonical and JSON-LD for category URLs, /robots.txt and /sitemap.xml. No fabricated ratings or thin locality doorway pages. Config PublicOrigin for canonical URLs.

ASAP scheduling: `isAsap=true` rejects a start more than 15 minutes ahead and canonicalizes the stored UTC start to server time plus five minutes. AvailableNow is required at request creation and never bypasses weekly working windows, Malta-date time-off exceptions or overlapping reservations. Acceptance and confirmation recheck the same windows/exceptions. Public `availableNow=true` discovery uses the same near-now interval (default duration 60 minutes), schedule and busy-booking checks; a future scheduled time with that flag is rejected.

Controlled staging fixture: `POST /api/admin/staging-demo/fixture {}` exists only in explicitly enabled Staging mode with an exactly matched isolated SQL database ending `_staging_demo`. Admin+CSRF required; returns unique fictional customer/worker login credentials and worker/category IDs, never privileged login access. Never log its response. Production cannot enable it. See STAGING-DEMO.md for indexing controls and the post-deployment lifecycle smoke.

Worker availability responses use `{id,dayOfWeek:0..6,startTime:"HH:mm",endTime:"HH:mm"}` on both backends. Weekdays are numbers (Sunday 0 through Saturday 6), not enum names; hours can be sent back to the availability endpoint without conversion.
